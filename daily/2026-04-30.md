# 2026年4月30日 - 第22课：大模型训练与推理工程

## 今日学习主题
**理解大模型从训练到推理的完整工程链路：分布式训练如何把千亿参数模型拆到成百上千张 GPU 上高效跑完，推理阶段如何用 KV Cache 和量化技术让模型跑得又快又省。**

## 为什么学这个？
上一课（多模态模型范式）我们看到了统一 Token 化如何让模型同时处理图像和文本。但一个现实问题一直被搁置：**这些千亿甚至万亿参数的模型，到底是怎么训练出来的？怎么部署上线的？**

从架构视角看，前 21 课我们一直在学「算法和架构」——模型长什么样、为什么这么设计。但如果不会训练和部署，再好的架构也只是论文里的图。训练与推理工程是从「论文」到「产品」的桥梁。

**在 AI 演进中的位置**：分布式训练工程（2020-）是与模型架构创新并列的关键能力。2020 年 GPT-3 的训练依赖微软的集群工程能力；2023 年 LLaMA 的开源让所有人能微调大模型，前提是你懂推理优化。**能训多大模型、能多快部署推理服务，决定了一个组织的 AI 技术天花板。**

## 核心概念解释

### 1. 内存墙——大模型训练的第一道关卡
- **直觉**：想象你要搬一个 10 吨重的箱子，但你的车只能装 2 吨。你需要要么把箱子拆开分多次运（模型并行），要么找更多车一起运（数据并行），要么把箱子压缩（量化）。
- **核心公式**：训练显存 ≈ 模型参数 × 2 bytes（FP16） + 优化器状态 × 8 bytes（Adam, FP32） + 梯度 × 2 bytes + 激活值
- **实际数字**：一个 70B 参数模型（如 LLaMA-70B），FP16 训练需要约 **420GB** 显存，而一张 A100 只有 80GB
- **代码对应**：Notebook 中的 `estimate_memory()` 函数可以直观看到各模型的显存需求

### 2. 数据并行（Data Parallelism / DDP / FSDP）
- **直觉**：你有一个食谱（模型），让 4 个厨师（GPU）分别用不同食材（数据分片）做同一道菜。每道菜做完后，4 个厨师交换心得（梯度同步），统一改进食谱。
- **DDP（Distributed Data Parallel）**：每张 GPU 持有完整模型副本，不同 GPU 处理不同数据。简单但显存浪费——每个 GPU 都要装下完整模型。
- **FSDP / ZeRO**：把模型参数、梯度、优化器状态**分片**到各 GPU，需要时再聚合。用通信换显存——同样的模型可以用更少的 GPU 训练。
- **ZeRO 三个阶段**：
  - ZeRO-1：只分片优化器状态 → 显存降 ~4x
  - ZeRO-2：分片优化器 + 梯度 → 显存降 ~8x  
  - ZeRO-3：分片优化器 + 梯度 + 参数 → 显存降 ~N（GPU数）倍

### 3. 张量并行（Tensor Parallelism）
- **直觉**：把一个大矩阵乘法切成几块，分给不同的 GPU 同时算。就像把一道大题拆成几道小题，几个人同时做。
- **核心机制**：Transformer 的 FFN 层和注意力头可以按列/行切分。比如一个 4096×16384 的权重矩阵，切到 4 张 GPU 上，每张只需处理 4096×4096。
- **适用场景**：**节点内**（NVLink 互联，带宽极高）。跨节点用张量并行通信量太大，不划算。
- **代表系统**：Megatron-LM（NVIDIA），Tensor Parallel = 节点内核心策略。

### 4. 流水线并行（Pipeline Parallelism）
- **直觉**：想象汽车流水线——车身焊接（GPU 0）→ 喷漆（GPU 1）→ 装内饰（GPU 2）→ 质检（GPU 3）。一辆车依次经过各工位。
- **核心机制**：把 Transformer 的不同层分配到不同 GPU。比如 24 层模型分 4 份，GPU 0 负责 1-6 层，GPU 1 负责 7-12 层，以此类推。
- **主要问题**：「气泡」——前面的 GPU 在工作时，后面的 GPU 空闲等待。微批处理（Micro-batching）可以缓解。
- **适用场景**：**跨节点**（通信量小，只需要在层边界传递激活值）。

### 5. 3D 并行——工业界标准方案
- **直觉**：把三种策略组合使用——**节点内用张量并行**（NVLink 快），**跨节点用流水线并行**（通信少），**全局用数据并行**（扩规模）。
- **实际案例**：GPT-4 训练据报道使用了 ~25000 张 A100，必然是 3D 并行。假设每 8 张卡（1 个节点）做 TP=8，然后 PP=4 跨节点，最后 DP 覆盖全局。
- **Notebook 对应**：可视化图清晰展示了三种并行方式的差异。

### 6. KV Cache——推理加速的核心
- **直觉**：自回归生成就像写作文——每写一个新字，你不需要重新读前面写过的每个字再做笔记；你只需要看新写的字，然后参考之前记好的笔记。KV Cache 就是 Transformer 的「笔记」。
- **核心机制**：生成第 t 个 token 时，前 t-1 个 token 的 K 和 V 向量已经在之前的步中算过并存下了。只需要算新 token 的 Q，然后和缓存的 K、V 做注意力。
- **加速效果**：对于长度为 N 的序列，无 Cache 总计算量是 O(N²)，有 Cache 降到 O(N)。实际加速可达 **10-50x**。
- **代价**：KV Cache 占显存。长上下文（100K tokens）场景下，KV Cache 显存可能超过模型本身。

### 7. 量化（Quantization）——用更少的位存储权重
- **直觉**：把照片从 PNG（无损）压缩成 JPEG（有损但肉眼几乎看不出）。模型权重从 FP16 压缩到 INT8 甚至 INT4，精度损失很小但体积大幅缩小。
- **INT8 量化**：2x 压缩，精度损失几乎可忽略
- **INT4 量化**：4x 压缩，精度损失可控（配合 GPTQ/AWQ 等算法）
- **关键价值**：INT4 量化让 70B 模型从 4 张 A100 降到 1 张——**部署成本降 4 倍**

## 关键公式直觉

| 概念 | 公式/方法 | 直觉解释 |
|------|----------|----------|
| 训练显存 | 模型 × 2B + 优化器 × 8B + 梯度 × 2B + 激活值 | 一个参数训练时占 ~20 bytes（含 Adam） |
| ZeRO-3 显存 | 总显存 / GPU 数 | 每张 GPU 只存 1/N 的模型 |
| KV Cache 显存 | 2 × 层数 × 隐层维度 × 序列长度 × batch × 2B | K 和 V 各需要一份，长上下文时这个值很大 |
| 量化节省 | 模型大小 × (原位数 / 新位数) | INT4 比 FP16 省 4 倍空间 |
| AllReduce 通信 | 2 × 模型大小 × (N-1)/N | N 张 GPU 的梯度同步，DDP 的主要开销 |
| TP 通信 | 每层 2 次 AllReduce | 前向和反向各一次，依赖 NVLink 高带宽 |

## 常见问题

**Q: FSDP 和 DeepSpeed ZeRO 有什么区别？**
A: 本质思路一样（分片优化器/梯度/参数）。FSDP 是 PyTorch 原生实现，和 PyTorch 生态无缝集成；DeepSpeed 是微软独立框架，功能更丰富（支持更多优化策略）。选哪个主要看你现有的技术栈。对于大多数场景，FSDP 已经足够好用。

**Q: 为什么不直接用最先进的量化？精度不丢吗？**
A: 好问题。量化确实会丢精度，但大模型有一个有趣特性：**参数越多，量化容忍度越高**。因为单个权重的重要性被分摊了——1000 亿个参数中，几个权重不够精确影响很小。GPTQ 和 AWQ 等算法会智能选择哪些权重需要更高精度，哪些可以激进压缩。

**Q: 训练和推理的并行策略一样吗？**
A: 完全不同。训练需要前向+反向+梯度同步，通信量大，适合 3D 并行。推理只有前向，瓶颈是显存带宽而非计算。推理的优化重点是 KV Cache 管理（如 vLLM 的 PagedAttention）、连续批处理（Continuous Batching）和量化。

**Q: 作为一个架构师，我需要关心到什么程度？**
A: 至少要理解「为什么 7B 模型单卡能跑，70B 就不行」「为什么推理时第一个 token 慢、后面快」「为什么同样的模型，不同推理框架性能差 5-10 倍」。这些决定了你的系统架构设计——选择什么模型、用什么硬件、怎么预估成本。

## 本课总结
1. **训练核心挑战是显存**：70B 模型训练需 ~420GB，远超单卡 80GB，必须分布式
2. **三种并行策略各有所长**：数据并行最简单、张量并行节点内最快、流水线并行跨节点最省通信
3. **3D 并行是工业标准**：TP（节点内）+ PP（跨节点）+ DP（扩规模）的组合
4. **KV Cache 是推理标配**：避免重复计算，将生成速度提升 10-50x
5. **量化让部署成本降 4 倍**：INT4 让 70B 模型从 4 卡变单卡
6. **架构师要关心的是成本-性能权衡**：不是最贵的就是最好的，合适的才是最好的
